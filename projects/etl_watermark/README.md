# etl-watermark — идемпотентная загрузка с водяным знаком

## Простыми словами

Загрузку почти всегда приходится запускать повторно: упала сеть, поправили
данные, переехал сервер. Если делать это наивно, строки задваиваются или теряются.
Инструмент грузит инкрементально, обновляет строки по бизнес-ключу вместо вставки
дублей и помнит, до какой даты данные уже приняты.

**Где применяется:** любой конвейер «источник → хранилище», где повторный запуск
и догрузка за прошлые дни — обычное дело.

**Как запустить:** `python -m projects.etl_watermark.cli demo`

Мини-ETL, который можно перезапускать без страха: повторный прогон не
дублирует строки, падение на середине не теряет данные, а состояние загрузки
видно в журнале прогонов.

## Что умеет

- **upsert по бизнес-ключу** (`client_id` + `dt`) — повторная загрузка обновляет
  строки, а не добавляет новые;
- **водяной знак** (`etl_watermark`) — до какой даты данные уже загружены;
  перезаливка старого дня не откатывает его назад;
- **журнал прогонов** (`etl_run`): статус, число попыток, сколько строк пришло /
  записано / схлопнуто как дубликаты, ошибка;
- **retry с backoff**: источник передаётся фабрикой, поэтому повторная попытка
  перечитывает его заново, а не «продолжает» с середины;
- **дедупликация внутри батча** (последняя версия строки побеждает);
- **dry-run** — посчитать объём, ничего не записав;
- **backfill по дням** — каждый день отдельным прогоном со своей записью в журнале.

## Запуск

```bash
python -m projects.etl_watermark.cli demo
python -m projects.etl_watermark.cli status --table client_daily_amount
```

```
1) первая загрузка за день          rows_written=40
2) повторная загрузка того же дня   строк в таблице: 40, записано: 40
3) источник отдал обновлённые значения  обновлено: 40, всего строк: 40
4) backfill за три дня              прогонов: 3, строк: 120, водяной знак: 2026-11-03
```

## Почему именно так

| Решение | Альтернатива | Почему выбрано это |
| --- | --- | --- |
| upsert по ключу | `DELETE` + `INSERT` партиции | не нужен эксклюзивный доступ к партиции и не теряются строки при падении между шагами |
| журнал в БД | лог Airflow | состояние переживает перезапуск планировщика и доступно SQL-запросом |
| источник как фабрика | итератор | retry обязан перечитать источник; итератор после исключения уже израсходован |
| водяной знак в отдельной таблице | `MAX(dt)` по факту | `MAX` по большой партиционированной таблице дороже, чем чтение одной строки |

## Тесты

```bash
python -m pytest projects/etl_watermark -q
```

Проверяется: первая загрузка, идемпотентный повтор, обновление изменённых
значений, схлопывание дубликатов батча, retry транзиентной ошибки, запись
постоянного сбоя в журнал, dry-run, backfill и монотонность водяного знака.

**В резюме:** «etl-watermark — идемпотентный ETL: upsert по бизнес-ключу,
водяной знак, журнал прогонов, retry с backoff, backfill по дням».
