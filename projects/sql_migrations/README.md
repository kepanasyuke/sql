# sql-migrations — миграции с контролем дрейфа

## Простыми словами

Схема базы меняется вместе с кодом, и надо, чтобы на всех окружениях она была
одинаковой, а изменение можно было откатить. Инструмент применяет пронумерованные
миграции атомарно, хранит контрольные суммы файлов и замечает, если уже
применённую миграцию кто-то отредактировал.

**Где применяется:** релизы схемы, локальные стенды, проверка в CI.

**Как запустить:** `python -m projects.sql_migrations.cli demo`

Простой, но аккуратный мигратор для SQLite: нумерованные файлы, секции
`up`/`down`, журнал с контрольными суммами, атомарное применение и защита от
параллельного запуска.

## Что умеет

- **каталог миграций** `NNNN_name.sql` (порядок — по номеру, дубликаты версий и
  кривые имена отсекаются на старте);
- **секции в файле**: `-- +migrate up` и `-- +migrate down` — откат описан рядом
  с изменением, а не «где-то в отдельном файле»;
- **атомарность**: схема и запись в журнал применяются в одной транзакции;
  ошибка в середине файла не оставляет половину таблиц;
- **контроль дрейфа**: в журнале хранится SHA-256 файла; если применённую
  миграцию отредактировали, `status` покажет `DRIFT`, а `apply` откажется
  работать — иначе прод и репозиторий расходятся незаметно;
- **блокировка** в БД (`schema_lock`): два процесса не применят миграции
  одновременно;
- `apply --to N` — докатить до версии, `down --version N` — откатить конкретную.

## Запуск

```bash
python -m projects.sql_migrations.cli demo
python -m projects.sql_migrations.cli --dsn artifacts/db.sqlite3 status
python -m projects.sql_migrations.cli --dsn artifacts/db.sqlite3 apply --to 2
python -m projects.sql_migrations.cli --dsn artifacts/db.sqlite3 down
```

```
версия | миграция                 | состояние | checksum
     1 | create_clients           | APPLIED   | 0a1f7c9d3b2e4f10
     2 | add_segment              | APPLIED   | 5d2c8e1a9f0b3c77
     3 | active_clients_view      | PENDING   | 9e4b1a7c2d8f5063
```

## Почему контрольная сумма обязательна

Классический инцидент: миграцию применили в проде, потом «поправили опечатку» в
файле. У разработчика схема соответствует новой версии файла, у прода — старой,
и никто об этом не знает, пока не упадёт загрузка. Хеш в журнале превращает это
в явную ошибку на этапе `apply`.

## Техническая деталь

`sqlite3.executescript` в legacy-режиме делает неявный `COMMIT` перед запуском
скрипта — из-за этого «транзакция вокруг файла» перестаёт быть транзакцией
(тест на откат это ловит). Поэтому скрипт разбивается на утверждения и
выполняется по одному внутри явной транзакции (`BEGIN IMMEDIATE … COMMIT`).

## Тесты

```bash
python -m pytest projects/sql_migrations -q
```

Проверяется: сортировка и разбор секций, отказ от кривых имён и дубликатов,
идемпотентность, `apply --to`, обнаружение дрейфа и блокировка применения,
откат схемы, полный откат частично применённой миграции и запрет параллельного
применения через `schema_lock`.

**В резюме:** «sql-migrations — мигратор с журналом и контрольными суммами:
атомарное применение, обнаружение дрейфа, up/down, блокировка от параллельного
запуска».
