# logwatch — разбор логов и алертинг

## Простыми словами

Приложение пишет логи, но читать их начинают, когда уже что-то сломалось. Хочется,
чтобы поток ошибок сам превращался в понятные алерты — и при этом не спамил
сотней одинаковых сообщений. Инструмент разбирает логи, считает пороги по окну
времени и склеивает повторы одной проблемы в один алерт со счётчиком.

**Где применяется:** дежурство по сервису, разбор инцидента после факта, выгрузка
метрик в Prometheus/Grafana.

**Как запустить:** `python -m projects.logwatch.cli analyze --demo --prom artifacts/metrics/logwatch.prom`

Потоковый разбор логов приложения и nginx-аксесслогов с пороговыми правилами по
временному окну и дедупликацией алертов. Метрики выгружаются в формате
Prometheus textfile — то есть их видно в общем дашборде рядом с DQ и SLA.

## Что умеет

- **два формата на входе**: nginx combined и JSON-лог приложения (ts, level,
  path, status, duration_ms), мусорные строки пропускаются;
- **правила**: серия `5xx` за окно, уровень `error`, regex по сообщению
  (`pool exhausted`, `deadlock`), медленные запросы;
- **окно и порог**: 3 ответа `5xx` за 60 секунд, а не «любой 500» — иначе один
  случайный ретрай клиента выглядит как авария;
- **дедупликация**: повтор той же проблемы (метод + маршрут + статус) в пределах
  окна не создаёт новый алерт, а считается в `suppressed` и попадает в
  следующий выпущенный алерт;
- **Prometheus-метрики**: `logwatch_events_total`, `logwatch_alerts_total{rule,severity}`,
  `logwatch_suppressed_total`, `logwatch_open_alerts{severity}`;
- exit-код 1 при наличии P1 — годится как гейт в CI/дежурный скрипт.

## Запуск

```bash
python -m projects.logwatch.cli analyze --demo --prom artifacts/metrics/logwatch.prom
python -m projects.logwatch.cli analyze --file nginx.log --json
```

```
строк разобрано: 42
алертов: 6, подавлено повторов: 3
  [P2] app.error: GET /api/clients/17 503 x1 — ошибки в логе приложения
  [P2] app.error: POST /api/transfer 500 x1 — ошибки в логе приложения
  [P1] db.pool_exhausted: POST /api/transfer 500 x1 — проблемы с пулом соединений БД
  [P3] http.slow_request: POST /api/transfer 500 x1 — медленный запрос
```

## Почему дедупликация — ключевая часть

Один сломанный эндпоинт под нагрузкой даёт сотни `5xx` в минуту. Без дедупа
дежурный получает поток одинаковых строк и перестаёт читать канал — классический
alert fatigue. Здесь проблема живёт как один алерт с счётчиком, а число
подавленных повторов сохраняется, чтобы после инцидента было видно масштаб.

## Тесты

```bash
python -m pytest projects/logwatch -q
```

Проверяется: парсинг обоих форматов и пропуск мусора, порог по окну, истечение
окна, дедупликация с накоплением `suppressed`, срабатывание level/regex/latency
правил, содержимое Prometheus-экспорта и exit-код CLI.

**В резюме:** «logwatch — потоковый алертинг по логам: правила с окном,
дедупликация (alert fatigue), Prometheus-экспорт, exit-код для дежурных скриптов».
